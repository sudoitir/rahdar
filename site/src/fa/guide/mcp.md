# سرور MCP

Rahdar از [Model Context Protocol](https://modelcontextprotocol.io) پشتیبانی می‌کند، پس یک دستیار می‌تواند *«چرا `ORDERS.DLQ` انباشته شده»* را روی کلاسترهای واقعی شما پاسخ دهد، به‌جای حدس‌زدن.

سطح در معرض، ابزارهای **مبتنی بر قصد** است — `diagnose`، `message_action`، `artemis_config_change` — نه آینه‌ای از REST API. یک آینه، context مدل را صرف لوله‌کشی می‌کند و سرهم‌کردن تشخیص را به خودش وامی‌گذارد؛ این ابزارها به‌جایش به شکل خودِ پرسش‌ها ساخته شده‌اند ([ADR-0045](/reference/adr/0045-mcp-server-is-a-capability-surface)، انگلیسی).

## گرفتن یک کلید

وارد شوید ← منوی آواتار ← **Account** ← **API keys** ← **New key** ← زمان انقضا، دامنه و مجوزهایی که باید حمل کند و در صورت نیاز **ابزارهای MCP** مجاز را انتخاب کنید ← مقدار را کپی کنید. فقط یک بار نمایش داده می‌شود.

- **انقضا.** هر کلیدی منقضی می‌شود، حداکثر به اندازهٔ بیشینهٔ عمر تعیین‌شده برای نصب پس از ساخت (به‌طور پیش‌فرض ۹۰ روز، *Settings ← API tokens ← Maximum lifetime*). کم‌کردن این بیشینه کلیدهای موجود را بی‌درنگ کوتاه‌تر می‌کند.
- **ابزارها.** کلیدی که به ابزارهای مشخصی محدود شده فقط همان‌ها و `rahdar_help` را می‌بیند؛ ابزارهای دیگر نه فهرست و نه توصیف می‌شوند، و فراخوانی آن‌ها دقیقاً همان پاسخ ابزاری ناموجود را می‌گیرد.
- **چرخش.** **Rotate** یک رمز تازه می‌سازد و رمز قبلی را در بازهٔ هم‌پوشانی (به‌طور پیش‌فرض ۲۴ ساعت) فعال نگه می‌دارد، تا پیکربندی دستیار بدون قطعی به‌روز شود. کلید مجوزها و زمان انقضایش را نگه می‌دارد.
- **محدودیت‌ها.** هر کلید در دقیقه ۶۰۰ درخواست و هم‌زمان ۸ درخواست، و هر کاربر روی همهٔ کلیدهایش در دقیقه ۱٬۲۰۰ درخواست مجاز است. هر پاسخ `RateLimit-Limit`، `RateLimit-Remaining` و `RateLimit-Reset` دارد و درخواست اضافی `429` همراه با `Retry-After` می‌گیرد.
- **مصرف** تعداد درخواست‌های روزانهٔ هر کلید را همراه با موارد ردشده، محدودشده و ناموفق نشان می‌دهد. مدیرانی که مجوز *See and revoke every user's API tokens* دارند همهٔ کلیدها را در **Admin ← API keys** می‌بینند؛ کلیدهای بلااستفاده علامت می‌خورند و هر کلیدی را می‌توان باطل کرد ([ADR-0136](/reference/adr/0136-token-rotation-lifetime-cap-limits-and-usage)، انگلیسی).

## اتصال

`POST /mcp`، روی همان origin رابط کاربری، با کلید به‌عنوان bearer token.

```json
{
  "mcpServers": {
    "rahdar": {
      "type": "http",
      "url": "https://rahdar.example.com/mcp",
      "headers": { "Authorization": "Bearer as_..." }
    }
  }
}
```

بدون کلاینت هم می‌شود آزمودش:

```bash
curl -s https://rahdar.example.com/mcp \
  -H "Authorization: Bearer as_..." \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

## منبع‌ها، نقش‌ها و سیستم‌ها

ابزارها یک منبع را با **شناسهٔ استاندارد** آن نام می‌برند، مثل `artemis.queue/orders`؛ همان `id` که `list_resources` در هر ردیف برمی‌گرداند، همراه با `kind` و `kindLabel` که سیستم به آن می‌دهد. آرگومان‌ها بر اساس چیستیِ منبع نام دارند: `subscription`، `destination`، `resource` (هدف چرخهٔ حیات) و `target`. `list_resources` همان `role` را می‌گیرد که باید فهرست شود — یکی از `destination`، `subscription`، `route`، `connection`، `channel`، `consumer` و `producer` — و در صورت نیاز یک `kind`.

ابزاری که فقط برای یک سیستم بروکر وجود دارد، شناسهٔ آن سیستم را پیشوند دارد: `artemis_config`، `artemis_config_change`، `artemis_config_diff`، `artemis_divert_lifecycle`، هشت ابزار `kafka_*` و `setup_review`. فقط به کلیدی عرضه می‌شود که بتواند کلاستری از آن سیستم را بخواند، و فراخوانی‌ای که کلاستر سیستم دیگری را نام ببرد خطای ابزاری می‌گیرد که می‌گوید آن کلاستر چه سیستمی را اجرا می‌کند.

## قرارداد ایمنی

دستیاری که یک API مدیریتی در دست دارد، دقیقاً همان‌جایی است که مدل ایمنی باید کسل‌کننده و صریح باشد. این یکی هست:

- **یک کلید هرگز از مالکش فراتر نمی‌رود.** دسترسی‌ها در هر فراخوانی با دسترسی‌های *زندهٔ* مالک اشتراک گرفته می‌شوند، پس محدودکردن یک فرد بی‌درنگ کلیدهایش را هم محدود می‌کند ([ADR-0046](/reference/adr/0046-mcp-authenticates-with-existing-api-tokens)، انگلیسی).
- **تغییرها به‌طور پیش‌فرض dry-run اند.** یک اجرای مخرب واقعی افزون بر آن نیاز دارد `confirm` برابر نام خودِ اشتراک یا مقصد باشد — که پرسشی جدا از `override` مربوط به سقف انبوه است و `confirm` هرگز آن را برآورده نمی‌کند.
- **تغییر Kafka اول پیش‌نمایش می‌شود و سپس نگه داشته می‌شود.** `kafka_preview_offset_reset` می‌گوید هر پارتیشن چه چیزی را رد یا دوباره می‌خواند، چه کسانی هنوز گروه را در دست دارند، و یک `etag` برمی‌گرداند؛ `kafka_reset_offsets`، `kafka_set_topic_config` و `kafka_abort_transaction` فقط روی `etag` پیش‌نمایش خود اجرا می‌شوند، اگر وضعیت عوض شده باشد به‌عنوان کهنه رد می‌شوند، و هرجا دروازهٔ تأیید روشن است تا تأیید نگه داشته می‌شوند. اجرای واقعی همچنین به `confirm` برابر با نام گروه، موضوع یا شناسهٔ تراکنشی نیاز دارد، و `kafka_set_topic_config` و `kafka_abort_transaction` به‌طور پیش‌فرض فقط پیش‌نمایش می‌دهند (`dryRun`). مثل هر ابزار تغییردهنده‌ای، وقتی نصب فقط‌خواندنی است پنهان می‌شوند.
- **هر فراخوانی ممیزی می‌شود**، خواندن‌ها هم، به‌صورت `MCP_TOOL_CALL` به نام مالک و با نام کلید ضمیمه‌شده (`ada [token: laptop-agent]`)، همراه با نام ابزار، کلاستر و نتیجه. ردیف‌هایی که یک تغییر می‌نویسد، شامل dry runها، زیر آن قرار می‌گیرند ([ADR-0137](/reference/adr/0137-one-gate-on-the-mcp-transport)، انگلیسی).
- **کل نصب را می‌توان فقط‌خواندنی کرد.** *Settings ← MCP server ← Read-only* همهٔ ابزارهای تغییردهنده را برای همهٔ کلیدها پنهان و رد می‌کند، هر `confirm` ای که داده شود. یک کلید فقط‌خواندنی همان کلیدی است که فقط مجوزهای خواندن دارد.
- **کلاستری که کلید بر آن دسترسی ندارد** با این پاسخ برمی‌گردد: *«چنین کلاستری وجود ندارد، یا این کلید بر آن دسترسی ندارد»* — بدون نام‌بردن از مجوزی و بدون تأیید هیچ id ای.

## کشف

`rahdar_help` یک ابزار است، نه یک منبع اختیاری؛ و یک کاتالوگ واحد schemaها، متن راهنما، منبع و دستورالعمل‌های سرور را می‌سازد — پس نمی‌توانند با هم اختلاف پیدا کنند ([ADR-0054](/reference/adr/0054-mcp-discovery-is-a-tool-not-a-resource)، انگلیسی).
