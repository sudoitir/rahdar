Two brokers are paging you. Open one console.

Rahdar is an open-source operations console for Apache ActiveMQ® Artemis and Apache Kafka®. Every cluster you run sits in one estate, every number says how sure it is, and nothing destructive runs before you have seen what it will do.

02:53The estate

Both systems, one list, worst first.

Without Rahdar this is a management console tab per Artemis broker and kafka-consumer-groups.sh in a terminal. With it, every cluster is in one estate, health is judged on one scale, and every backlog is in one table: Artemis queues and Kafka consumer groups side by side, each under its own name.

Kafka lag is an estimate, and says so. It is the gap between where a group committed and where each partition ends, sampled a moment ago. A partition the group never committed to has no lag to add, so it is left out and the total tells you. Select a row to see what it is made of.

How Rahdar reads lag

02:56The cause

Two partitions are stuck behind a transaction nobody will finish.

ledger-writer reads only committed records. A settlement job died half-way through a transaction on payments-2 and payments-5, so the consumer cannot read past the transaction's first record, the last stable offset, while new records keep arriving behind it.

Activity → Transactions flags a hanging transaction at the top: past its timeout, or its producer gone. Abort… first previews what the abort does and which partitions it unblocks. Then you press and hold, and it is audited.

Rahdar refuses to abort a transaction that is still live.

Transactions in the Kafka guide

03:04The reset

Skip what nobody needs. See it before it happens.

The ledger is catching up. risk-reports is not a ledger: it scores payments as they happen, and replaying the stalled half hour would raise alerts about payments that settled long ago. The team decides it should start reading at 03:00.

Reset offsets… previews every partition: where the group is, where it would move, how many records it would skip or read again. Kafka only lets an empty group move, so a group with members is refused, by name, before anything is armed.

Where an approval gate is on, the reset then waits for a second person, and re-checks the group when it runs. Every reset is audited with the offsets before and after, so it can be reset back.

Reset offsets

03:09The other pager

Meanwhile, ORDERS.DLQ on the Artemis pair.

Artemis's own console shows one broker at a time. Rahdar asks every node which one is serving, on every cycle, and never trusts the configuration for it: two live nodes in one pair is a split-brain alert, not a surprise.

Every queue on every node is in one table, sorted by depth. The dead-letter queue is the first row, with no consumer. Moving its messages back is previewed as a dry run that changes nothing, and purge is pressed and held.

Moving messages safely

03:14The assistant

An assistant can propose the change. A person still approves it.

Rahdar is an MCP server. An assistant reads your real clusters with an API key that never exceeds its owner's grants, and every call lands in the same audit trail as a person's.

  • Eight kafka_* tools: groups and lag, the reset and its preview, topic configuration, ACLs, aborting a transaction.
  • A change runs only against the preview it was shown, is refused as stale if the group moved, and must name what it changes.
  • Where the approval gate is on, the change waits for a person, like yours did.
The MCP server

What it runs on, today and next.

Rahdar talks to brokers through OpenBroker, an open-source broker SDK with a driver per system. Each system keeps its own words and its own limits, and the shared screens say which is which.

Apache ActiveMQ® Artemis

2.33.0 and later
  • Topology with HA roles polled from every node
  • Every queue, address, consumer and connection across nodes
  • Flow, SQL over messages, message capture
  • Move, retry, expire, delete and purge, each with a dry run
  • Declared broker configuration and setup review
The guide

Apache Kafka®

3.0 and later, KRaft and ZooKeeper
  • Consumer, share and classic groups with per-partition lag
  • Offset reset with a preview, and approval where the gate is on
  • Topic configuration checked by the broker before it applies
  • ACLs with effective access before and after
  • Hanging transactions, brokers and the controller quorum
  • Browse by partition, offset or time; truncate with its reach stated
The Kafka guide

RabbitMQ

Coming next. Not supported yet.

Planned on the roadmap as another OpenBroker driver. Until it ships, Rahdar does not register RabbitMQ.

Easy on the broker

Reads are batched per node, polled in tiers and rate-limited. Rahdar must never be the reason a broker falls over.

A preview before anything destructive

Every destructive call can run as a dry run, and states its reach: the resource, the nodes or partitions, and how much goes.

Audited before it runs

Every change is recorded before the broker call and updated with its outcome, by people, API keys and assistants alike.

Honest about what it cannot do

An unavailable action stays visible with its reason. An estimate says it is one, and an unknown number is never shown as zero.

$ git clone https://github.com/sudoitir/rahdar && cd rahdar
$ just up   # two Rahdar replicas, HAProxy and Postgres, pinned to the latest release

Your brokers already exist. You register them in the UI, from an Artemis management URL or Kafka bootstrap servers, and a check reaches every broker before anything is saved.
